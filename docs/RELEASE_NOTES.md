## Integration — 2026-08-14 · Secure Guest Access

Deployed to **AURA Integration** (`os-one-cwp-production.up.railway.app`).
Not promoted to Production; that remains a deliberate act through AURA-Release.

### User experience

The captive portal now offers **two workflows from one page**.

- **Existing open guest access — unchanged and still the default.**
  Open guest WLAN → user agreement → *Connect to the Internet* → gateway
  authorization → internet, forwarded to the page the guest was opening. Same
  copy, same button, same position, same behaviour.
- **New: optional Secure Guest Access.** A second, clearly-labelled option on
  the same consent form — *Accept & Connect Securely* — that names the encrypted
  network and its security mode. Choosing it grants internet access exactly as
  before and then offers guided setup for the secure WLAN.
- **Platform-aware setup.** One action, *Set Up Secure Wi-Fi*, resolving to
  whatever actually works on the device in the guest's hand.
- **QR and manual fallbacks**, with manual setup available on every platform.
- Secure setup can be abandoned at any point. The page says the guest is already
  online before it says anything else, and offers *Skip and continue to the
  internet* throughout.

### Existing guest workflow

```
Open guest WLAN → User Agreement → Connect to the Internet → Internet Access
```

**Unchanged and available.** A guest can still connect, accept and use the
internet without ever seeing or selecting Secure Guest Access. The branch is a
single boolean with a default of `false`, read once after authorization; the
consent gate, the presigned `/ext_approval.php` URL and the gateway callback are
identical on both paths. If the secure WLAN is unconfigured or unreadable the
second option is simply not drawn.

### Secure guest workflow

```
Open guest WLAN → Captive Portal → Secure Guest Access → Agreement
  → gateway authorization → Secure Wi-Fi setup → Skynet (WPA2 Personal)
```

### Supported platforms

Measured against the secure WLAN's real configuration — WPA2-Personal (AES),
PMF disabled, ASCII passphrase.

| Platform | Primary mechanism | Works? | Notes |
|---|---|---|---|
| iPhone | Apple configuration profile | Yes | Unsigned — iOS shows *Unverified* on the install screen. Installs and works. Finish in Settings. |
| iPad | Apple configuration profile | Yes | Same. QR also offered, since an iPad is a plausible second screen. |
| macOS | Apple configuration profile | Yes | Install from System Settings › General › VPN & Device Management. |
| Android | Manual entry | Yes | Android has **no** web-installable Wi-Fi profile. QR is offered for *another* device — a phone cannot scan its own screen. |
| Windows | Manual entry | Yes | Plus a downloadable WLAN profile for `netsh wlan add profile`. |
| Unknown / other | Manual entry | Yes | Plus QR where the security mode allows it. |

Wi-Fi QR (`WIFI:T:WPA`) and the Apple payload both work because the network is
WPA2-Personal. On a WPA3-only network neither can express the mode, and both are
withdrawn rather than offered as buttons that fail silently.

### Backend

- `SecureOnboardingService` — session lifecycle, artifact accounting, join
  verification.
- `CredentialProvider` abstraction with one implementation today,
  `skynet-gateway`, which reads the SSID, security mode and passphrase from the
  **live gateway** rather than from configuration.
- Platform adapters producing Apple `.mobileconfig`, Windows WLAN profile XML,
  Wi-Fi QR SVG, and a manual-entry view.
- Server-side platform detection: Client Hints first, user-agent second, plus a
  client-reported `maxTouchPoints` so an iPad — which sends a macOS user-agent —
  is not treated as a Mac. Captive-portal webviews are detected and change what
  is offered.
- New REST surface under `/api/v1/onboarding/sessions`.

### Database (PostgresCWP)

Migration `20260814120000_secure_onboarding`, purely additive, applied and
verified with no drift.

- `GuestSession.onboardingRequested BOOLEAN NOT NULL DEFAULT false` — every
  existing row keeps working.
- New `OnboardingSession` table with `OnboardingStatus`, `OnboardingMethod` and
  `OnboardingPlatform` enums.
- Indexes on `tokenHash` (unique), `sessionId`, `clientMac`, `status`,
  `createdAt`, `expiresAt`, and `(status, createdAt)`.
- `sessionId` FK is `ON DELETE SET NULL`: an onboarding record is an audit
  artifact in its own right and must survive session retention sweeps.
- **No credential column exists.** The passphrase is never persisted.

### Gateway

**Inspected, not modified.** `GET /v1/services/{id}` for the WLAN configuration
and `GET /v1/stations` for join verification — both reads. No WLAN, role, AAA
policy, topology or radio binding was created or changed, and the secure WLAN's
passphrase was not rotated.

Transition detection is real: the controller reports `serviceId` per station, so
a device that moves from the guest WLAN to the secure WLAN keeps its MAC and
changes its `serviceId`. That is the only thing that sets `COMPLETED`. Verified
against the live controller with a MAC the gateway reported on the secure WLAN —
`state: completed`, access point `AP5020-PVT-02`.

### AURA

Clients → Guest Users gains one **Secure Wi-Fi** column, populated from the
portal's internal guest API. Deliberately kept out of the main status column:
whether a device reached the encrypted WLAN is a different question from whether
it may use the guest network, and collapsing them would make one unanswerable.
Only *On secure Wi-Fi* claims a join; *Profile sent* and *QR shown* say what the
portal did.

### Security

- Onboarding is authorised by an opaque 32-byte token in an HttpOnly,
  `SameSite=Lax`, `Secure` cookie, stored only as SHA-256 and compared in
  constant time. The onboarding id is in URLs and is never sufficient alone.
- Credential-bearing responses are `no-store, no-cache, must-revalidate,
  private` with `nosniff` and `no-referrer`; profiles are served as attachments
  with correct content types.
- `POST`, not `GET`, for the passphrase — it cannot be bookmarked, prefetched,
  linked, restored by back-navigation or left in history. It is returned only
  after an explicit tap.
- Rate limiting per onboarding session and per route.
- "No such session", "wrong token" and "expired" all answer `404`, so the
  difference cannot be used to enumerate ids. No stack traces or raw API errors
  reach a guest.
- Log validation performed after testing: build and runtime logs searched for
  the Skynet passphrase, the ECP shared secret, the session secret, the internal
  API token, the gateway password, `presharedKey`, mobileconfig bodies, QR
  payloads and onboarding token values. **Zero occurrences.**
- Browser validation per platform: 623 KB of JavaScript bundles, rendered DOM,
  `localStorage`, `sessionStorage` and the URL all searched for the passphrase.
  **Zero occurrences** before the explicit reveal.

No secret values appear anywhere in this document, in the repository, or in the
frontend.

### Known limitations

- **Randomised MAC addresses.** A device using a private Wi-Fi address per SSID
  appears on the secure WLAN as a different station, so the join cannot be
  correlated. This produces `exhausted` and an honest message, never a false
  `COMPLETED`.
- **Unsigned Apple profile.** iOS shows *Unverified* in red on the install
  screen. It installs and works. Signing needs a trusted code-signing identity,
  which does not exist in this environment.
- **iOS Captive Network Assistant** cannot install a configuration profile or
  reach Settings. The page detects it and leads with *Open in Safari*
  (`x-safari-https://`), with manual setup — which works inside the assistant —
  beside it. The Safari hand-off scheme is not guaranteed on every iOS build, so
  a plain link is offered underneath.
- **Android has no web-installable Wi-Fi profile.** Manual entry is the primary
  mechanism, by necessity rather than by preference.
- **Windows cannot self-install** the WLAN profile from a browser; the guest
  runs one `netsh` command, so it is a secondary option behind manual entry.
- Device emulation is not a phone. Final validation is a real handset.

### Future: PPSK

Per-device PPSK does not exist yet, and nothing here pretends otherwise: the
credential is declared `perDevice: false` and no page calls it "your" password.

The seam is `CredentialProvider`. `describe()` returns the non-secret network;
`issue(context)` returns credential material and receives the onboarding id,
client MAC and platform — everything a per-device provider needs to mint a key.
`credentialProviderFor(context)` already takes the session context rather than
being a constant, so a PPSK provider is a second implementation plus a branch
there. `SecureNetworkCredential.perDevice` and `expiresAt` exist for it, and
`OnboardingSession.credentialProvider` records which provider answered so old
sessions stay interpretable.

Nothing above that seam changes: not the iPhone or Android flows, the QR
handling, the manual fallback, platform detection, the onboarding session model,
the audit events, the join verification, or any page.
